Shared matching and construction kernel
======================================

Selection
---------
--kernel c|x86|hybrid is independent of the language and semantic profile.
All modes retain the C runtime and host services. The selector chooses kernel
operations: x86 uses linked machine code; hybrid chooses qualified operations
by domain and measurement. C is the default. --kernel-stats writes requested mode, implementation calls,
resource charges and host-service counts to stderr. Repeated contradictory
kernel selections, and the legacy x86-flat backend combined with a non-C
kernel, are rejected. Ordinary answer output is unchanged.
Counters describe instrumented kernel operations. In particular, zero graph
imports or callbacks does not mean zero host work: indexing, interning,
successor construction, allocation and publication remain C services.

C uses independent C algorithms. x86 executes prelinked images compiled from
the authored p1 programs and the direct assembly batch entry described below.
The production library contains no t-ISA interpreter.
The integration exposes no interpreter switch, component flag or fallback.
Its policy and observation controls use independent C oracles. The compiler
reference model is confined to the vendored compiler development checks. Hybrid
currently uses C for scalar matching, general construction and prepared rule
batches: the assembly batch has not beaten equally prepared C consistently.
Grounded
primitives, storage, indexes, ownership services and publication remain host
services in every mode.

Ordinary matching enters the shared policy component through decoded,
one-way, epoch, linear-plan and stored-candidate entrypoints. Complete
BindingValue context words and authoritative frame reads are retained. A
plain shared-DAG specialization also admits declared live lexical frames;
undeclared frames, lists and richer values retain their general policy walk.
A failed private DAG solve publishes no bindings, then the general walk
retains its own failure-prefix behavior. Operational failure is incomplete
work, not a negative logical verdict.

The relation-specialized native_query implementation contains C matching
and construction. Strict x86 mode decline it before effects and use
the indexed general consumer. C and hybrid retain its batching and joins.
This boundary avoids labeling that C implementation as native execution.

Sessions and snapshots
----------------------
kernel.h provides scoped sessions, solve/probe, checkpoints, binding deltas
and output bundles. NmHostValue carries source syntax and its complete host
context as two words. Source owners, callback contexts and read pins remain
borrowed; they must outlive their use. Each session's source view is stable
until release. Checkpoints belong to one session generation. Restoring one
restores the private substitution and retains consumed fuel.

A tell may introduce bindings. A probe reports ENTAILED, REFUTED or OPEN
without adopting its trial bindings. Resource, fuel, invalidation, interruption
and provider faults have distinct statuses. OPEN supplies no permission to
assume a guard. A private substitution snapshot is not a complete language
branch or AnswerSpace: the host retains the surrounding constraints and
custody separately.

CettaKernelOutput owns an immutable materialized graph. Its graph, origins
and release operations are common to C and x86. Repeated roots retain
multiplicity. Unbound variables retain complete keys. Output origins name
the source before instantiation; they do not claim it is already materialized.
The caller revalidates its commit token before publishing any result.

Reusable constructors
---------------------
constructor.h compiles a finite fixed shape into an immutable plan. A plan
is a constructor over explicit formal ports. Every execution supplies those
ports with full contextual values; admission of bindings and binder scopes
belongs to the caller. Normalizing the complete port bundle shares its work,
and a prelinked linear executor builds the fixed structure. No JIT is used.

The plan key includes owner generation, semantic policy and lexical context.
The source syntax owner and pin remain live until the plan is released. Each
execution uses its own stable session view. Binding-dependent results are
not cached between executions. Generative locals and captured variables are
selected by the caller's port values, not guessed from printed variable names.
Wrong port keys defer; mismatched owner/policy/context keys invalidate the plan.

Constructor receipts distinguish activation, port normalization, prepared
private storage and executor work. No output is returned on failure, even
when the complete private graph was written before the final fuel check.

Automatic plan caching requires a stable term-owner generation and retirement
contract; pointer identity is not used as a persistent cache key. Clients with
explicit custody can retain plans through the public interface.

tcalc's unifier and term builder
--------------------------------
tcalc's x86 kernel is two p1 programs over tcalc's own term store
(tcalc_bridge.h, tcalc_native.c): native_tcunify (tcunify.metta) solves one
equation as unify_c does, and native_tcbuild (tcbuild.metta) lists how to
make terms with the assignments applied, as resolve_from and close_from make
them. Each call borrows the TcNode[] nodes, items, local and unknown tables,
trail, work stack and walk records as its regions; tcstore.metta holds their
shared reading. Neither program makes a term. The unifier hands back a term to
close, a table to grow or a walk epoch to renew, and resumes; the builder's
list (fresh unknowns, expressions to make) is made by the core in list order,
which is the core's own order, so fresh unknowns and term ids come out as in
C. Interning can relocate the pools, so every call renews the borrowed
pointers; the programs keep indices only, and every table stays below 2^31
entries. tests/tcalc/tcalc_native_unify_test.c compares both with the core's
C, assignment for assignment.

Resident rule batches
---------------------
batch.h declares the borrowed call layout once for C and assembly. The prepared
rule format is the existing FlatPlan: first local occurrences name selected
fields, repeated occurrences become equality edges, and makes project fields
or constants. A program retains these immutable plans across calls and extends
the cache when rules are appended. Term ids are stable; pool pointers are not.

The admitted profile is step one over a ground canonical state, with flat
positive patterns and makes. Rules with tells, checks, nested local patterns,
fresh output locals or heads bound by earlier patterns retain the general
indexed matcher. The last case requires its dynamically bound head index;
using an unbound candidate run there would discard existing index pruning.
Other step disciplines also retain the general implementation.

C selects the indexed candidate runs. One bounded C or assembly call then
enumerates candidate tuples, checks distinct takes and persistent reads,
applies equality guards, and writes private selections and make-field ids.
The assembly entry directly borrows TcNode[], uint32_t children and row ids;
it does not import NmNode graphs, allocate, call host functions or publish.
The independent C executor uses the same prepared inputs and result format.

Explorer owns reusable cursor and output buffers. C drains complete private
records through the existing interner, successor builder and publication
protocol. Interning can relocate term pools, so the next bounded call renews
all borrowed pointers. Cursors retain indices only. Each activation borrows
a complete physical copy of the small immutable plan metadata.

The call boundary checks lengths, field references, physical spans, aliasing
and carried prefix shapes. Candidate proposals and record activations each
consume one native fuel unit; a failed activation retains its charge. Output
capacity and proposal quantum bound individual calls. END alone denotes a
complete scan; YIELD and EXHAUSTED do not establish absence. These charges
are separate from the language's semantic step budget.

Consumers and host effects
--------------------------
tcalc's unifier writes its assignments and trail entries into the core's own
tables, so the caller's rollback undoes them as it undoes C's. A rule's made
rows are built in one walk epoch, sharing one memo; another activation starts
a new one. Native status never becomes a successful empty result.

Transform retains occurrence cursors and its firing/store protocol. Eligible
firings use the term carrier; other host control keeps the same selected
matching/observation operations. Results are prepared privately, occurrences
are revalidated, and the host publishes once. A terminal failure after host
effects never retries through another implementation.

Qualification
-------------
The vendored source package and authored component inputs are hash-pinned.
Startup compares linked code against its expected image. Development checks
compare IR emission against those bytes. Normal builds
need no neighboring tcalc checkout. Image regeneration is a development task.
Fields are declared in the component layout sources and generated into C;
physical C layouts and tags also receive static assertions.

Tests cover complete contextual results, failed-prefix rollback, captures and
fresh scopes, stale keys, repeated answers, source reclamation, allocation and
fuel boundaries, linked-byte mutations and reference-matcher leaks. Standalone
C clients can omit the native provider and retain their reference path.

This is experimental functional integration. The prepared rule path removes
the previous per-pair graph conversion and speeds up C as well as x86. On the
current resident workloads, assembly is near C rather than a consistently
faster implementation. General native matching still has substantial module-
scale overhead; full native performance acceptance remains open.
tools/benchmark_native_kernel.py records equal-result whole-process
comparisons with statistics disabled. Source ownership admission, foreign contracts,
compiler fidelity and machine-code refinement remain distinct obligations.
The separate combined formal goal is not completed by these tests.
